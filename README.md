# portable-mcu-hal
Portable C hardware abstraction layer for ARM Cortex-M. Switch between STM32, nRF52, Silicon Labs EFR32 and TI MSPM0 by changing one macro. No RTOS, no build system, no dynamic allocation.

# mcu-hal 

A thin, vendor-agnostic peripheral wrapper for ARM Cortex-M MCUs —
STM32, nRF52, Silicon Labs EFR32, and TI MSPM0. Write your business logic
once against a small, stable API; swap the underlying vendor SDK by
changing one preprocessor macro.

**Status:** early development — all eight peripherals (GPIO, UART, I2C,
SPI, ADC, Timer, PWM, Flash) are frozen and have adapters written for all five
target macros, each with a passing unit test and a measured flash/RAM
footprint (see "Testing and footprint" below). The `os_port.h` RTOS
shim is still undesigned. Not ready for production use — no adapter
has been compiled against a real vendor SDK or run on real hardware
yet. See `docs/development-plan.md` for the staged
build-out.

## Why this exists

Vendor SDKs (STM32Cube, nrfx, Gecko SDK, MSPM0 driverlib) are not
portable across each other. Full frameworks like Zephyr solve this, but
require adopting their kernel, build system, and scheduler. This project
takes a narrower approach: a thin contract layer over the official
vendor SDK you already use, with the RTOS binding kept as a separate,
optional shim — so it works bare-metal, with FreeRTOS, or with whatever
you already run. No build system to adopt; drop the files into your
existing IDE project (STM32CubeIDE, IAR, Keil, Simplicity Studio, Code
Composer Studio) and define one macro.

See `docs/architecture.md` for the full design rationale.

## How it works

```
Your business logic  →  hal_wrapper.h (this library's public API)
                      →  <vendor>/<peripheral>/hal_port_<vendor>.c (thin adapter)
                      →  Official vendor SDK (unchanged, you supply it)
```

## STM32: CubeMX integration notes

STM32 is the one vendor here where "the SDK" means CubeMX-generated
project code, not just a library you link against — most of a real
STM32 project's peripheral setup is autogenerated, not written by hand.
This wrapper is designed around that rather than fighting it, but it's
worth understanding exactly how the two pieces fit together before you
wire this in, since the two real risks below look similar but aren't:

- **Handle variables are never redefined, only referenced.** Every
  STM32 adapter that needs a peripheral handle (`huart2`, `hi2c1`,
  `hspi1`, `hadc1`, `htim6`, ...) declares it `extern` and relies on
  CubeMX's own generated `usart.c`/`i2c.c`/`spi.c`/`adc.c`/`tim.c` to
  own the one real definition. An `extern` is a declaration, not a
  definition — there's no dual-definition risk here at all. (If your
  CubeMX project doesn't enable a given instance, that `extern` becomes
  an unresolved symbol at link time instead — a loud, intentional
  failure, not a silent one; trim the adapter's handle table to match
  what you actually enabled.)
- **Re-running `HAL_xxx_Init()` is not a dual-definition either — it's
  an ordinary function you can call as many times as you like.** Three
  adapters (UART, SPI, Timer) call it again after touching exactly one
  field (`BaudRate`, `CLKPolarity`/`CLKPhase`, or `Init.Period`), on
  the assumption CubeMX's own `MX_xxx_Init()` already configured
  everything else correctly the first time (it runs automatically,
  before your own `main()` code). Two adapters (I2C, ADC) never call
  it again at all — their init parameters are advisory-only, since too
  much of the underlying config (I2C's `TIMINGR` clock timing, ADC's
  full conversion setup) can't be safely reconstructed at runtime. See
  each peripheral's caveats below for which case applies.
- **The real dual-definition risk is HAL's weak completion callbacks.**
  `HAL_UART_TxCpltCallback`/`RxCpltCallback`/`ErrorCallback`,
  `HAL_I2C_MasterTxCpltCallback`/`MasterRxCpltCallback`/`ErrorCallback`,
  `HAL_SPI_TxCpltCallback`/`RxCpltCallback`, `HAL_ADC_ConvCpltCallback`,
  and `HAL_TIM_PeriodElapsedCallback` are all declared `__weak` in HAL
  itself — exactly one strong definition is allowed per project. This
  wrapper's async-tier adapters *are* that one definition, for whichever
  peripherals you enable via `HF_ENABLE_*`. If your own code (very
  commonly, CubeMX's `/* USER CODE BEGIN 4 */` block in `main.c`) also
  defines one of these same function names, you'll get a genuine
  `multiple definition of '...'` linker error — remove your own
  definition (or don't enable that peripheral's async tier here) rather
  than trying to keep both. This wrapper never touches CubeMX's own
  generated ISR vectors (`USARTx_IRQHandler`, `TIMx_IRQHandler`, etc.
  in `stm32fxxx_it.c`) — those stay exactly as generated and call into
  HAL, which then reaches whichever weak callback is actually defined.

"Written, unverified" means: written against the vendor's documented
API and, where a specific detail was in question, checked against the
vendor's own source — but none of these thirty-five adapter files have
been compiled against a real SDK checkout or flashed to real hardware
yet. See `docs/development-plan.md` for what's still open on each.

**TI MSPM0 GPIO caveat:** unlike the other vendors, `hf_gpio_init()` on
MSPM0 can only set pin *direction* (input vs. output) — pull resistors,
open-drain, and drive strength live behind a separate per-pin IOMUX
register that `hf_gpio_t` has no way to address, and are normally
configured through SysConfig's pinmux GUI instead. Calling
`hf_gpio_init()` with `HF_GPIO_INPUT_PULLUP`, `HF_GPIO_INPUT_PULLDOWN`,
or `HF_GPIO_OUTPUT_OPENDRAIN` on this vendor returns `false` rather
than silently configuring only the direction — see the pull/open-drain
asymmetry table in `docs/architecture.md`.

**UART caveats:**
- **Silicon Labs `sl_gpio`/`sl_i2c` target**: unlike GPIO and I2C,
  there's no independent "current" UART driver on this vendor —
  `hal_port_silabs_slgpio_uart.c` deliberately uses the same raw emlib
  calls as the classic adapter (`hal_port_silabs_uart.c`), since the
  nearest "current" option, `sl_iostream_usart`, is confirmed to wrap
  the same classic peripheral underneath with no confirmed-stable
  public callback or non-blocking-read primitive to build the async
  tier on safely. See `docs/architecture.md`'s "UART, part three" for
  the full reasoning.
- **TI MSPM0**: same kind of flagged, not-independently-confirmed
  constant names as the I2C adapter (TI's docs domain and community
  forum are both blocked in the environment this was written in) —
  four names in `ti/uart/hal_port_ti_mspm0_uart.c`, listed in the file.
  Also: some MSPM0 parts expose a simpler UART API without the
  `_Main_` in the function names — check which your part/instance uses.
- **All five adapters**: `hf_uart_tx_callback_t` carries no success/
  failure signal — a failed async transfer clears the busy flag
  silently rather than firing the callback and implying it succeeded.

**I2C caveats:**
- **STM32**: `hf_i2c_init()`'s `clock_hz` is advisory only — STM32's
  I2C clock timing (`TIMINGR` on newer families) depends on the clock
  tree and isn't a runtime Hz-to-register formula, so this adapter
  assumes CubeMX's generated init already configured it correctly.
- **nRF52** and **Silicon Labs `sl_i2c`**: both need SCL/SDA pins
  supplied directly at init (no CubeMX/SysConfig-style pre-muxing step
  for these peripherals) — `nrf/i2c/hal_port_nrf52_i2c.c` and
  `silicon_labs/i2c/hal_port_silabs_slgpio_i2c.c` each carry an
  explicit, clearly marked pin table you need to edit to match your
  board's wiring before use.
- **TI MSPM0**: two specific constant names in `ti/i2c/hal_port_ti_mspm0_i2c.c`
  (an RX-FIFO-ready status flag and the async tier's interrupt-index
  constants) rely on driverlib's established naming pattern rather
  than a confirmed source read — TI's docs domain and community forum
  are both blocked in the environment this was written in. Flagged
  explicitly in the file; verify against your installed SDK.

See `docs/architecture.md`'s I2C section for the full reasoning behind
each of these, including how `hf_i2c_write_read`'s repeated-START
requirement is met differently on each vendor.

**SPI caveats:**
- **STM32**: your CubeMX SPI configuration must have hardware NSS
  management disabled (Software NSS, or NSS not used) — this wrapper
  drives chip-select itself through the `cs_pin` argument on every
  call, and a hardware-driven NSS output would fight that. `clock_hz`
  is advisory only, same category of limitation as I2C's `clock_hz`.
- **Silicon Labs, both targets**: classic EFM32/EFR32 SPI
  (`hal_port_silabs_spi.c` / `hal_port_silabs_slgpio_spi.c`, both built
  on `platform/emdrv/spidrv`) and classic UART
  (`hal_port_silabs_uart.c` / `hal_port_silabs_slgpio_uart.c`) run on
  the exact same USART hardware peripheral and IRQ vectors. Enabling
  both a SPI adapter and a UART adapter for the **same** USART instance
  in the same project produces a duplicate interrupt-vector link error
  — trim each file's instance table so UART and SPI use disjoint USART
  instances if you need both.
- **TI MSPM0**: two names in the async tier of
  `ti/spi/hal_port_ti_mspm0_spi.c` (`DL_SPI_getPendingInterrupt`,
  `DL_SPI_disableInterrupt`) rely on driverlib's established naming
  pattern rather than a confirmed source read — TI's docs domain and
  community forum are both blocked in the environment this was written
  in. Flagged explicitly in the file; verify against your installed SDK.
- **All five adapters**: like UART's, `hf_spi_tx/rx_callback_t` carry
  no success/failure signal — a failed async transfer clears the busy
  flag (and deasserts chip-select) silently rather than firing the
  callback and implying it succeeded.

See `docs/architecture.md`'s "SPI, part two" section for the full
reasoning behind each of these, including why chip-select composes the
existing GPIO API rather than a new concept.

**ADC caveats:**
- **STM32**: resolution is advisory only — `hf_adc_init()` doesn't call
  `HAL_ADC_Init()` itself (that would re-run CubeMX's whole peripheral
  configuration), so it assumes CubeMX's own generated init already
  selected 12-bit resolution (the reset default on most parts).
- **Silicon Labs, classic (`TARGET_SILABS`)**: `hal_port_silabs_adc.c`
  uses the simpler, non-APORT `input`/`ADC_SingleInput_TypeDef`
  channel-selection field. If your part has an APORT crossbar, edit
  `s_adc_channels[]` in that file to use `posSel`/`ADC_PosSel_TypeDef`
  constants instead.
- **Silicon Labs, current (`TARGET_SILABS_SLGPIO`)**: unlike every
  other peripheral this vendor exposes, ADC's current-generation
  hardware (IADC) is a genuinely different peripheral block from
  classic ADC, not a newer driver over the same registers — many
  Series 2 parts have IADC only. `hal_port_silabs_slgpio_adc.c` carries
  more genuinely-unconfirmed specifics than any other adapter in this
  repo (several struct/macro names follow Silicon Labs' own published
  IADC example-project conventions rather than a directly re-quoted
  struct definition) — flagged explicitly in the file; cross-check
  against Simplicity SDK's own "iadc_single_conversion" example
  projects before relying on it. Its channel table (`s_adc_channels[]`,
  GPIO port+pin based) is an EDIT-ME table you must match to your
  board's wiring, same treatment as this vendor's I2C SCL/SDA pins.
- **TI MSPM0**: ADC12 results are indexed by a conversion-memory slot
  (`DL_ADC12_MEM_IDX`), not read back by raw channel number — this
  adapter deliberately reconfigures MEM_IDX 0 to the requested channel
  on every call rather than relying on SysConfig's usual fixed
  MEM_IDX-to-channel mapping. Six enum-constant arguments to
  `DL_ADC12_configConversionMem()` weren't independently confirmed and
  use conservative disabled-style defaults — flagged explicitly in the
  file; verify against your installed SDK.
- **All five adapters**: like UART's/SPI's, `hf_adc_callback_t` carries
  no success/failure signal — a failed async conversion clears the busy
  flag silently rather than firing the callback and implying it
  succeeded.

See `docs/architecture.md`'s "ADC, part two" section for the full
reasoning behind each of these.

**Timer caveats:**
- **STM32**: `period_us` assumes CubeMX's generated init already set
  TIM6/TIM7's prescaler so one tick equals one microsecond — a common
  CubeMX configuration choice for exactly this purpose, but not
  something this adapter can verify or configure itself. One-shot mode
  is software-enforced (the elapsed callback stops the timer itself)
  rather than using STM32's own hardware One-Pulse Mode, which is an
  output-channel feature and not a fit for a headless timer.
- **Silicon Labs, classic (`TARGET_SILABS`)**: same advisory-`period_us`
  situation, assuming a 1 MHz HFPERCLK-after-prescale tick rate — edit
  the `prescale` field in `hal_port_silabs_timer.c` if your part's
  HFPERCLK isn't already 1 MHz.
- **Silicon Labs, current (`TARGET_SILABS_SLGPIO`)**: genuinely
  different API shape from every other Timer adapter — `sl_sleeptimer`
  is a software timer *service* (one shared hardware timer backs many
  independent handles), not a "pick the vendor's Nth peripheral"
  driver. It also only exposes millisecond-granularity time conversion,
  so `period_us` is rounded up to whole milliseconds on this vendor
  specifically — a real, permanent resolution loss, not an oversight.
- **TI MSPM0**: uses `DL_TimerG` (general-purpose), deliberately leaving
  `DL_TimerA` (advanced/PWM-capable) free for PWM. Several `DL_Timer_*`
  config field values are flagged as not independently confirmed in
  `ti/timer/hal_port_ti_mspm0_timer.c` — verify against your installed
  SDK.
- **All five adapters**: like ADC's, `hf_timer_callback_t` carries no
  success/failure signal — there's no bus-failure-style outcome for a
  period elapsing.

See `docs/architecture.md`'s "Timer, part two" section for the full
reasoning behind each of these.

**PWM caveats:**
- **STM32**: uses TIM2/TIM3 (general-purpose, 4-channel), disjoint from
  Timer's TIM6/TIM7 (basic timers have no output-compare channels at
  all). `freq_hz` assumes a 1 MHz post-prescale tick, same advisory
  situation as Timer's `period_us`.
- **nRF52**: structurally different from every other PWM adapter —
  `nrfx_pwm` is an EasyDMA sequence player, not a compare-register
  write, so `hal_port_nrf52_pwm.c` keeps a persistent per-instance duty
  buffer that a live `hf_pwm_set_duty()` call updates and re-arms.
  Needs an EDIT-ME output-pins table, same situation as this vendor's
  I2C SCL/SDA table — nrfx_pwm has no separate pin-mux step. `freq_hz`
  is genuinely accurate here (this project owns the clock config
  outright), unlike most other vendors' advisory-only frequency.
- **Silicon Labs, classic (`TARGET_SILABS`)**: the one vendor where
  Timer and PWM genuinely share hardware — uses TIMER2/TIMER3,
  disjoint from Timer's TIMER0/TIMER1; verify your part has enough
  TIMER blocks before enabling both. Pin routing to a physical output
  is real register-level work classic emlib's `TIMER_InitCC()` doesn't
  provide on its own, and Silicon Labs has at least three incompatible
  schemes for it across device generations — only the newer Series 2
  `GPIO->TIMERROUTE`/`ROUTEEN` scheme is implemented; older Series 2 and
  Series 0/1 parts need their own scheme substituted in, flagged EDIT
  ME in the file rather than guessed at.
- **Silicon Labs, current (`TARGET_SILABS_SLGPIO`)**: uses `sl_pwm`, a
  real current-generation driver confirmed to sit directly on the same
  classic TIMER hardware as the classic adapter (not a genuinely
  different peripheral) — but it does handle its own clock enable, GPIO
  pin mode, and pin routing internally, none of which the classic
  adapter gets for free. `freq_hz` is genuinely accurate here (a real
  improvement over classic's advisory-only assumption); `duty_millipercent`
  is rounded to the nearest whole percent, a real, permanent resolution
  loss — `sl_pwm_set_duty_cycle()` only takes a plain 0-100 percent.
- **TI MSPM0**: uses `DL_TimerA`, the peripheral Timer's own adapter
  deliberately reserved for this. Several `DL_Timer_*` config field
  values are flagged as not independently confirmed, same situation as
  this vendor's Timer adapter.
- **All five adapters**: fixed at active-high output and edge-aligned
  (up-counting) mode — not configurable in v1. Inverted polarity,
  center-aligned mode, and duty/frequency readback are all backlog.

See `docs/architecture.md`'s "PWM, part two" section for the full
reasoning behind each of these.

**Flash caveats:** unlike every peripheral above, there is no `hf_flash_t`
instance type — internal flash is one singular region per chip, so the API
is addressed directly by raw chip memory address. **Never erase or write
the flash region your own code/vector-table/const-data lives in** — every
adapter here uses each vendor's normal, flash-resident blocking erase/
program call, not a RAM-executed variant; see `hf_flash_t`'s header comment
in `include/hal_wrapper.h` for the full cross-vendor safety finding behind
this rule.
- **STM32**: F4-family reference. Erase granularity is **not uniform** —
  F4's sector table has 16 KB/64 KB/128 KB sectors in the same bank, so
  `hf_flash_erase_size()` looks the address up in a table rather than
  returning one constant; EDIT that table for your exact part.
- **nRF52**: uniform 4096-byte pages via `nrfx_nvmc`. Does not account for
  SoftDevice (BLE stack) coexistence — direct NVMC access while a
  SoftDevice is active can stall the radio; use `nrf_fstorage` instead if
  you add BLE to a project using this adapter.
- **Silicon Labs, both targets**: both `TARGET_SILABS` and
  `TARGET_SILABS_SLGPIO` use the same classic `em_msc.h` (MSC) calls —
  there is no distinct current-SDK driver at this level (Silicon Labs'
  current-generation flash story, NVM3, is a wear-leveled store built on
  top of the same MSC peripheral, and `hf_flash_t` is explicitly scoped to
  raw flash, not a filesystem). Page size varies by part's total flash
  size — EDIT the constant in both adapter files for your part.
- **TI MSPM0**: 1024-byte sectors (confirmed against `dl_flashctl.h`'s
  `DL_FLASHCTL_SECTOR_SIZE`), 64-bit flash words. The exact
  `unprotectSector`/erase ordering and the `FLASHCTL` base-pointer macro
  name are flagged as not independently confirmed — see the adapter's own
  header comment.
- **All five adapters**: no async tier (flash operations are rare,
  slow, one-at-a-time) and no RAM-executed erase/program variant — both
  backlog.

See `docs/architecture.md`'s "Flash" section for the full reasoning
behind each of these.

## SDK versions this wrapper targets

Vendor SDKs aren't static, and two of the four vendors below (nRF52
and Silicon Labs) have — or are having — a live old-SDK → new-SDK
transition. Rather than silently picking one generation and leaving
the other unsupported, each vendor adapter below states plainly which
SDK generation(s) it covers and why.

| Vendor | Adapter files | SDK generation covered |
|---|---|---|

PWM uses general-purpose timers (TIM2/TIM3) instead, since basic timers have no output-compare channels at all. Flash targets the F4 family's non-uniform sector table (see the Flash caveats above). |
| nRF52 | `nrf/gpio/hal_port_nrf52.c`, `nrf/uart/hal_port_nrf52_uart.c`, `nrf/i2c/hal_port_nrf52_i2c.c`, `nrf/spi/hal_port_nrf52_spi.c`, `nrf/adc/hal_port_nrf52_adc.c`, `nrf/timer/hal_port_nrf52_timer.c`, `nrf/pwm/hal_port_nrf52_pwm.c`, `nrf/flash/hal_port_nrf52_flash.c` | **Both** the legacy **nRF5 SDK** and the current **nRF Connect SDK**. | Silicon Labs EFR32 | `silicon_labs/{gpio,uart,i2c,spi,adc,timer,pwm,flash}/hal_port_silabs*.c` **and** `silicon_labs/{gpio,uart,i2c,spi,adc,timer,pwm,flash}/hal_port_silabs_slgpio*.c` | **Two real adapters per peripheral for GPIO, I2C, ADC, Timer, and PWM**, though for several different kinds of reasons. Timer splits because of a different API *shape* — classic emlib's `TIMER` is a "pick the vendor's Nth hardware peripheral" driver, while the current SDK's `sl_sleeptimer` is a software timer *service* backed by one shared hardware timer underneath, exposing unlimited independent handles instead of instance numbers. PWM splits for a third reason again: the current SDK's `sl_pwm` is a real driver, but confirmed to be a thin convenience wrapper directly over the same classic TIMER hardware the `TARGET_SILABS` PWM adapter uses — not a genuinely different peripheral, just a genuinely different (and more convenient, better-behaved) API surface over it. Flash's 1024-byte `DL_FLASHCTL_SECTOR_SIZE` is confirmed directly against `dl_flashctl.h`. |

None of these are pinned to one exact numbered SDK release (e.g. a
specific STM32Cube_FW_F4 version, or nRF5 SDK 17.1.0 vs. an older
17.x). The adapters were written against the vendor's documented,
version-spanning API surface and, for anything in question, checked
against the vendor's own current source — but `CLAUDE.md` and
`docs/gpio-api-reference.md` both call out: **verify signatures against
the exact SDK version you actually install**, since vendor APIs do
shift between releases even within one generation.

## Testing and footprint

Every adapter file has a unit test and a measured flash/RAM footprint on its
real target instruction set, **kept inside that vendor's own folder** — a
`<vendor>/tests/` and `<vendor>/footprint/` per vendor (e.g. `stm/tests/`,
`nrf/footprint/`), not one shared folder for all four, since copying just
`stm/` shouldn't hand you nRF52/Silicon-Labs/TI test data too:

```
make -C stm/tests report          make -C stm/footprint report
make -C nrf/tests report          make -C nrf/footprint report
make -C silicon_labs/tests report make -C silicon_labs/footprint report
make -C ti/tests report           make -C ti/footprint report
```

Both compile the real adapter `.c` files against hand-written fakes of the
vendor SDK headers they include, since no vendor SDK is installed in this
repo — see each vendor's own `tests/README.md` and `footprint/README.md`
for how that works and what it does and doesn't prove. Each vendor's
`TEST_REPORT.md` and `FOOTPRINT.md` have the last recorded results;
regenerate either after changing an adapter. The only shared piece is
`unity/` at the repo root (vendored [Unity](https://github.com/ThrowTheSwitch/Unity),
MIT licensed) — a third-party dependency, not vendor-specific test content.

**None of this is a substitute for compiling against a real vendor SDK and
running on real hardware** — that verification remains open for every
adapter in this repo, same standing gap noted throughout this README.
