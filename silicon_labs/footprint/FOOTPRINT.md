# Silicon Labs adapter flash/RAM footprint

Generated by `make -C silicon_labs/footprint report` against a real ARM
cross-compiler (`GNU size (xPack GNU Arm Embedded GCC x86_64) 2.42.0.20240614`), `-Os`. Each adapter `.c` file
is compiled standalone to a `.o` (never linked into a full firmware image - no
vendor SDK is installed in this environment) against the same fake emlib/
sl_gpio/sl_i2c/IADC headers `../tests/fakes/` uses for unit testing, since
compiling only needs declarations, not their behavioral bodies. Covers both
target macros this vendor ships - classic emlib (`TARGET_SILABS`, Cortex-M4)
and the current sl_gpio/sl_i2c/IADC drivers (`TARGET_SILABS_SLGPIO`,
Cortex-M33 - Series 2/3 parts use the M33 core). See "What these numbers do
and don't mean" below before quoting one out of context.

Sum of all 14 adapters' `.text`: **5062 bytes** - no real project
enables both generations at once (you pick one target macro), so treat this as
a ceiling, not a typical build. Useful as a regression baseline: re-run after
changing an adapter and diff against a committed copy of this file.

## What these numbers do and don't mean

- **Real compiler, real target ISA, real -Os.** This is genuinely how much
  flash each adapter's code costs on the core listed - not a host-machine proxy.
- **No vendor SDK is linked in.** Every `GPIO_*`/`USART_*`/`I2C_*`/`ADC_*`/
  `sl_gpio_*`/`sl_i2c_*`/`IADC_*`/`SPIDRV_*` call the adapter makes resolves
  to an external symbol with zero bytes charged here - the real Simplicity SDK's
  own flash cost is NOT included. These numbers are the wrapper adapter's *own*
  code only, the same scope this project's contract covers.
- **No linker garbage collection was run** (`--gc-sections` needs a full link),
  so a function only reachable from an unused code path (e.g. the async tier, if
  your project only calls the blocking one) is still counted here - real
  firmware with `--gc-sections` enabled would drop it.
- **.bss (RAM) is per-adapter static state** (ring buffers, busy flags, callback
  pointers) - real total RAM also depends on your linker script and whatever
  else runs on the same part.
- Compare classic vs. current loosely, not directly - Cortex-M4 and Cortex-M33
  have different instruction encodings and calling conventions, so a smaller
  number on one core isn't automatically "more efficient" than the other.
